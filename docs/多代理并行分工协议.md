# 多代理并行分工协议（1 主控 + N 子代理，共用一个 Gateway / 一个 .blend）

> 适用：DSH 主控（`role=main`）带若干子代理，全部打在**同一个 GUI 会话、同一份 .blend** 上。
> 一句话：**先分地，再发 grant，写时自报 scope，作业自己收。**
> 事实来源：`runtime/core/sessions/scopes.ts`、`grants.ts`、`write-authority.ts`、`runtime/core/queue/types.ts`；
> 参数名与端口只认 [配置参考](配置参考.md) 与 [操作教程](操作教程.md)，本文不新增参数。

## 0. 四条硬事实（其余都是展开）

| 事实 | 代码 | 对你的意思 |
|---|---|---|
| 一个会话只有一个 owner | 同机/同家族的调用方 `attach` 只拿 viewer（`is_mine=false`），无关 DSH 会话直接 `session_in_use` | 主控 hold 会话；子代理的写全部靠 grant |
| 写门只有一处 | `sessionWriteGate` 按**调用方自己声明的** `write_scope` 授权，缺省 `exclusive` | 写了什么 scope 就按什么判，声明即契约 |
| scope 六类 | `exclusive` / `collection` / `prefix` / `object` / `aspect` / `frames` | `aspect:` 按“面”切（world / render / camera / lights），`frames:` 按帧区间切（`1-60`）；`blender_py` 只能声明前四类 |
| 队列上限是四个数 | `DEFAULT_CAPACITY`：pending 64 / gpu 1 / cpu 2 / ownerQuota 8 | 并发形状由这四个数决定，先数作业再分人 |

## 1. 六种切法：一次只选一种

| 切法 | 怎么分 | 适用 | 反例 |
|---|---|---|---|
| objects | 按对象名/前缀把对象清单分给各人 | 场景里对象已经存在，或每人产出的名字可预知 | 两人都要改同一把椅子 = 必撞 |
| parts | 按部件/子装配切（座面、椅腿、扶手各一人） | 大件分件建模，最后合并 | 部件之间要布尔/贴合时，边界会来回改 |
| aspects | 按"面"切（建模 / 材质 / 灯光 / 机位） | 理想形态：四个人四种写 | 可用 `aspect:lights` / `aspect:camera`；但目录默认仍是 exclusive，必须显式 `write_scope`（见 §2） |
| time | 按帧区间切（1–60 / 61–120） | 长动画分段 | 可用 `frames:START-END`（区间相交才冲突）；仅静态 op，py 不行 |
| plan_then_do | 主控先只读出计划（`blender_op(op="catalog")`、`audit_*`），再派活 | 场景陌生、拆不准的时候 | 计划本身要改场景时会边规划边写，等于没分 |
| none | 不分，单 agent 串行 | 一个人十分钟能干完的活 | 硬拆成并行，冲突开销大于收益 |

选完切法再决定 grant：**objects/parts 落 `prefix` / `collection`；aspects 落 `aspect:lights` 之类；time 落 `frames:1-60`；plan_then_do 先跑只读再发 grant**。aspect/frames 只对静态 op 生效，`blender_py` 必须用对象级 scope。

## 2. 共享面只归一个 owner

共享面固定四个：**world / render / camera / lights**。它们不属于任何对象，改一次影响全场。

- 它们没有对象名前缀可挂，但可以走 `aspect:`：`aspect:lights` / `aspect:camera` / `aspect:render` / `aspect:world`。
- `exclusive` 与**任何** scope 都算重叠（任一侧 exclusive 即冲突）；而 `aspect:lights` 与 `prefix:CHAIR_A_` **不冲突**——这才是“建模 + 打光”并行的正解。
- 两条实操前提：① op 的目录默认是 `exclusive`，必须显式 `write_scope="aspect:lights"`，否则写门仍按 exclusive 判、当场 `scope_conflict`；② `blender_py` 不能声明 aspect/frames（写后对象校验认不出，会回 `invalid_params`），所以打光要走 `blender_op`。
- 仍然遵守“一个面一个 owner”：world / render / camera / lights 四者可以分给四个人，但同一个面不能两个人同时持有；真需要 `exclusive`（一次改多个面）时，退回串行。

反例：建模 agent 拿 `prefix:CHAIR_A_`、灯光 agent 拿 `aspect:lights`——可以并行；但如果灯光 agent 图省事发 `exclusive`，就会和建模 grant 相撞。正确做法是显式 `aspect:lights`，或等建模交付后再串行打光。

## 3. 对象名前缀约定，以及它和 prefix scope 的关系

`prefix` 是**纯文本前缀比较**：冲突判定双向 `startsWith`，覆盖判定单向 `startsWith`，对象归属也按 `startswith`。**代码不认识任何连接符**，连接符只是给人读的。

| 连接符 | 约定的含义 | 例子 |
|---|---|---|
| `_` | 领地 + 角色 + 序号，最常用；prefix 直接取到角色段 | `CHAIR_A_seat`、`CHAIR_A_leg_01` |
| `.` | 子部件/左右/Blender 自动重名后缀，必须放在前缀**之后** | `CHAIR_A_arm.L`、`CHAIR_A_seat.001` |
| `-` | 临时/草稿物，**不进任何 grant** | `WIP-chair`、`TMP-probe` |

三条硬规则：

1. **两人的前缀必须互不为前缀**：`prefix:CHAIR` 与 `prefix:CHAIR_A_` 会判重叠 → `scope_conflict`；`prefix:CHAIR_A_` 与 `prefix:CHAIR_B_` 才安全。
2. **别跨 kind 划同一批对象**：不同 kind 只有文本完全相同才算冲突（`collection:Seats` 与 `prefix:Seat` 不冲突），但一个按集合成员判、一个按名字判，重叠对象仍会被两边同时改。
3. **裸名字等于 collection**：`scopes="CHAIR_A"` 会被当成 `collection:CHAIR_A`，不是前缀；前缀必须写 `prefix:`。

`object:` 按对象名**精确匹配**，对象一改名授权就失效 —— 只用于少量固定对象。

## 4. scope 词汇与判定

| scope | 状态 | 判定方式 |
|---|---|---|
| `exclusive` | 可用 | 全场景；和任何 grant 都冲突 |
| `collection:名` | 可用 | 改完之后按集合**成员**归属（用 addon 回的真实成员，不看脚本自称） |
| `prefix:名` | 可用 | 对象名 `startsWith` |
| `object:名` | 可用 | 对象名精确相等 |
| `aspect:world` / `render` / `camera` / `lights` | 可用 | 同名才算重叠；只对静态 op 生效，`blender_py` 禁用（回 `invalid_params`） |
| `frames:START-END` | 可用 | 区间相交才算重叠，包含才算覆盖；同样只对静态 op 生效 |

⚠️ 两条后果：① **写一个解析不出来的 kind 不是“更窄”，而是“更宽”**——未知 kind 返回 null，scope 列表变空时写门补 `exclusive`；② aspect 的取值只做同名比较，写 `aspect:light`（少 s）不会报错，但会和 `aspect:lights` 互不重叠，等于各写各的——名字按上面四个写。

## 5. 失败码 → 具体动作

| 码 | 什么时候出现 | 立刻做什么 |
|---|---|---|
| `scope_conflict` | 发 grant 时与别人的活动 grant 重叠（回执带 `grant` 字段：holder + scopes） | 换个更窄、互不为前缀的 scope；或让持有人 `revoke`；确实要替换旧 grant 才用 `force=true`（会删掉重叠的旧 grant） |
| `scope_required` | 写没有覆盖 grant；或 `blender_py` 没声明 `write_scope`（回执 `is_mine` 能看出是"没授权"还是"不是你的会话"） | 补 `write_scope`，且要落在自己的 grant 覆盖范围内；纯读改用 `blender_see` / `blender_inspect` |
| `session_in_use` | 另一个 DSH 会话持有 owner（attach / release / heartbeat 都能报） | 同机仍可 viewer 只读；写要 owner `grant`；owner 心跳过期（子 30 s / 主 30 min）会自动回收，同机主控可 `release force=true` |
| `session_already_available` | 已经有一个 ready 的 user-gui 会话时又去 `start virtual-gui` | 直接 `attach`（自己的）或 viewer 读；要独立窗口先让 owner `release`，再 start |
| `queue_full` | 队列 pending 到达上限（默认 64，`DSH_BLENDER_QUEUE_PENDING` 可配），submit 直接被拒（回执带 `pending` / `limit` / `set`） | 不要重试轰炸；`blender_run(action="list")` 看谁在跑，等一条结束再交；或合并成一个 `action="worker"` 连续 exec |

## 6. 并发参数：默认值与查询方式

可配：`DSH_BLENDER_QUEUE_{GPU,CPU,PENDING,OWNER_QUOTA}`（env 优先）或配置文件 `features.queue.*`，详见[配置参考](配置参考.md) §12；下表是**默认值**，真值永远以回执为准。

| 参数 | 默认值 | 含义 |
|---|---|---|
| `ownerQuota` | 8 | 每个 owner（hostId + dshSessionId + agentId 三元组）同时 assigned/running 的作业数；queued 不计 |
| `gpu` | 1 | `kind="render"` 一律 GPU 槽，并存 1 个 |
| `cpu` | 2 | `kind="headless"` 默认 CPU 槽（`params.gpu=true` 才上 GPU） |
| `pending` | 64 | queued + assigned + running 的总数 |

查询方式（都在回执里，别背数字）：

- `blender_run(action="perf")` → `capacity`（含 ownerQuota）+ `slots.gpu/cpu`（used/total/reserved）+ `pending` + `byState`。
- `blender_run(action="list", owner="all")` → 每条作业的 `slot` / `priority` / `state`，翻页用 `limit`/`offset`。
- `blender_session(action="grants")` → 现有 grant 的 holder / scopes / `expiresInMs`。

## 7. 作业收尾：提交方负责到底

- `submit` 立即回 jobId，**没有同步模式**；后续只用 `status` / `wait` / `collect` / `cancel`。
- `wait` 默认 120 s、上限 600 s。**超时只表示"没等到"，不取消作业**：回执 `timed_out=true` + `still_running=true`，配合 `state` 看是在跑还是排队（`decision.reason`）。
- 收尾必须做两件事：① `blender_run(action="list", owner="me")`（`owner` 缺省就是 me）确认没有漏收的作业；② 对要产物的 id 跑 `wait`，日志/产物用 `collect`。
- 子代理有独立 `dshSessionId`，所以 `owner=me` 只看得到自己提交的；主控看子代理的作业用 `owner=<子代理 session id>` 或 `owner="all"`（父 agent 与同会话 main 都有权限）。
- `timed_out` 之后：先 `status` 看 `queued_ahead` / `decision.reason`（`quota` / `capacity` / `fifo`），再决定继续等还是 `cancel`；**不要重新 submit**。
- Gateway 换代时 running/assigned 会被标 `failed(gateway_restart)` + `lost=true`：id 与参数保留，要产物就用同一组参数重新 submit。

## 8. 可复现例子：两个子代理各建一把椅子

目标：主控 owner，`chair-a` / `chair-b` 各建一把，产出名字分别以 `CHAIR_A_` / `CHAIR_B_` 开头；灯光与机位留到最后由主控做。

```text
# ① 主控：认领会话，发两条互不为前缀的 grant
blender_session(action="status")
blender_session(action="attach", instance_id="<在 status 里看到的 instanceId>")
blender_session(action="grant", target_agent_id="chair-a",
                scopes="collection:CHAIR_A,prefix:CHAIR_A_", ttl_ms=1800000)
blender_session(action="grant", target_agent_id="chair-b",
                scopes="collection:CHAIR_B,prefix:CHAIR_B_", ttl_ms=1800000)
blender_session(action="grants")        # 确认两条：holder 不同、scopes 互不为前缀
```

```text
# ② 子代理 chair-a：每个写调用都自报 write_scope（必须被自己的 grant 覆盖）
blender_py(write_scope="prefix:CHAIR_A_", code="
import bpy
for name, loc in [('CHAIR_A_seat',(0,0,0.45)), ('CHAIR_A_leg_01',(0.2,0.2,0)),
                  ('CHAIR_A_leg_02',(-0.2,0.2,0)), ('CHAIR_A_leg_03',(0.2,-0.2,0)),
                  ('CHAIR_A_leg_04',(-0.2,-0.2,0))]:
    bpy.ops.mesh.primitive_cube_add(size=0.1 if 'leg' in name else 0.5, location=loc)
    bpy.context.object.name = name
")

# ③ 子代理 chair-b：同一份脚本，把 CHAIR_A_ 换成 CHAIR_B_、write_scope 换成 prefix:CHAIR_B_
```

```text
# ④ 各自收尾（谁提交谁收）
blender_run(action="list", owner="me")      # 必须只看到自己的作业，且都已终态
blender_run(action="collect", id="job-…")   # 要日志/产物时
```

两个保证：

- 名字以 `CHAIR_A_` 开头 → 落在 `prefix:CHAIR_A_` 内，`blender_py` 的作用域守卫不会报 `scope_violation`。
- 名字不在前缀内 → 守卫报 `scope_violation`，**新建对象会被删掉**；已经存在的对象只列在 `unrolled` 里（不回滚），得用 `blender_session(action="txn", op="restore")` 收拾。
- `ttl_ms` 默认 10 min、上限 1 h；被 grant 覆盖的写会按原 TTL 续期，多步子代理不会中途掉权限（长活仍建议显式给 `ttl_ms=1800000`）。

共享面（world / 灯光 / 机位）有两个合法做法：① 主控在 ④ 之后统一做（owner 恒放行）；② 现在就把 `aspect:lights` / `aspect:camera` 授给一个专门 agent，它与两条 prefix 互不冲突——但该 agent 的打光必须走 `blender_op` 并显式 `write_scope="aspect:lights"`，不能用 `blender_py`。

## 9. 验收清单（贴进交付说明）

- [ ] `scope_conflict` = 0：发 grant 一次成功，没有靠 `force=true` 抢别人的活。
- [ ] `scope_required` = 0：每个写调用都带 `write_scope`，且被自己的 grant 覆盖。
- [ ] `session_in_use` = 0：子代理全程 viewer，写靠 grant，没有 attach 被挡。
- [ ] `session_already_available` = 0：没有重复 `start virtual-gui`。
- [ ] `queue_full` = 0；`blender_run(action="perf")` 的 `pending` 始终在 64 以内。
- [ ] `scope_violation` = 0：每个子代理的产出名字都在自己前缀内。
- [ ] `blender_run(action="list", owner="all")` 收尾时只剩 completed / failed，没有"提交了没人收"的作业。
- [ ] 共享面只有一个写者，且它写的时候别人没在写对象。
- [ ] 最后的整体验收（`qc_render_views` / `audit_mesh`）由主控在共享面完成后跑一次。
