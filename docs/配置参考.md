# 配置参考

> 全部机器相关设置都在 `runtime/config.ts`（编译产物 `lib/runtime/config.js`）：
> **环境变量 → 配置文件 → 自动探测 → 内置默认值**。只有这一份实现；换机器只改配置，不改源码。
>
> **当前版本**：插件 **v3.3.0** · **6 个模型工具** · plan catalog **38 family / 270 op** · Blender 侧 addon **v2.0.0 / protocol 12** ·
> Gateway `127.0.0.1:39877` · addon 主动连接（无入站端口）。**唯一验收判据**：`doctor` 回 `kind=ok`。

---

## 1. 优先级链（高 → 低）

```text
┌ 1. 环境变量        DSH_BLENDER_*（见 §3）
├ 2. 配置文件        $DSH_BLENDER_CONFIG
│                    → <包根>/dsh-blender.config.json
│                    → ~/.dsh/dsh-blender.config.json
├ 3. 自动探测        工作目录（Windows %LOCALAPPDATA%\dsh-blender-rt；macOS ~/.dsh-blender-rt；取不到则 os.tmpdir()）
│                    blender.exe（macOS /Applications/Blender*.app；Windows Program Files / Steam；WSL /mnt/<盘>/…；再 PATH）
└ 4. 内置默认        Gateway 127.0.0.1:39877（addon 主动连接，无入站端口）· 租约 TTL 600000 ms · holder=plugin-pid-<pid>
```

**怎么确认当前生效的是什么**：

```bash
curl -sS http://127.0.0.1:39877/who | python3 -m json.tool | sed -n '/"config"/,/}/p'
# 或者让模型调：blender_session(action="doctor")   → 返回里的 config 段
```

`config` 段里会写明 `configFile`（用了哪个配置文件，没用到就是 `null`）、`workDir.from`、`blenderFrom`（`config` / `auto:install` / `auto:steam` / `auto:path` / `not-found`）。

## 2. 配置文件

复制样例并改名即可生效：

```bash
cp dsh-blender.config.example.json dsh-blender.config.json
```

| 键 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `workDir` | string | 自动 | 帧 PNG / 无头脚本 / 临时产物目录。**Windows 形式**（`D:\\work\\dsh-blender-rt`）；WSL 下会映射成 `/mnt/d/...`。必须"两端都能读写" |
| `blenderExe` | string | 自动 | blender 可执行文件。WSL 里给 `/mnt/d/.../blender.exe`（Windows 进程）；纯 Windows 给 `D:\\...\\blender.exe` |
| `addonHost` | string | `127.0.0.1` | 3.0.x addon 监听地址；3.1 addon 主动连接 Gateway，忽略此项（兼容保留） |
| `addonPort` | number | `9876` | 3.0.x addon 监听端口；3.1 addon 主动连接 Gateway，忽略此项（兼容保留） |
| `httpPort` | number | `39877` | 3.0.x 名称，等价于 Gateway 端口（3.1 优先用 `gatewayPort`；两台 Gateway 并存时改一台） |
| `gatewayPort` | number | `39877` | Gateway 唯一入站端口（env：`DSH_BLENDER_GATEWAY_PORT`） |
| `holder` | string | `plugin-pid-<pid>` | 写通道租约身份（多会话时便于分辨谁在写） |
| `leaseTtlMs` | number | `600000` | 租约有效期；持有者每次都续期，超时自动失效 |
| `blenderUserConfig` | string | `null` | 用户 Blender 配置目录（GPU 偏好所在）。**无头进程默认读不到它** → 想继承就设它并配合 `factory_startup=false`（env：`DSH_BLENDER_USER_CONFIG`） |
| `blenderUserScripts` | string | `null` | 用户 Blender 脚本目录（addon 所在），同上（env：`DSH_BLENDER_USER_SCRIPTS`） |
| `workerPort` | number | `9879` | 热无头 worker 的**起始**本地端口（与 Gateway 39877 区分；env：`DSH_BLENDER_WORKER_PORT`）。同名 session 复用；不同 session 按启动顺序顺延（9879/9880/…），`local_processes` 报每个 pid 的真实端口，不要写死 9879 |
| `features.virtualGui` | string | `auto`（Windows）/ `off`（Linux、macOS） | virtual-gui 能力门：`off` / `auto` / `on`。Windows V0 通过后默认 `auto`；Linux/macOS 默认 `off`，Linux 只接受显式 `on`（preview）（env：`DSH_BLENDER_VIRTUAL_GUI`） |
| `features.virtualGuiMax` | number | `4` | 同时存活的 virtual-gui 实例上限（1–16）；总内存 <16 GiB 或空闲内存 <4 GiB 时降到 2（env：`DSH_BLENDER_VIRTUAL_GUI_MAX`） |
| `features.queue.gpu` | number | `1` | 同时跑的 GPU slot 数（`kind=render`；`gpu=true` 的 headless 也走它）。**不随设备数自适应**，见 §12（env：`DSH_BLENDER_QUEUE_GPU`） |
| `features.queue.cpu` | number | `2` | 同时跑的 CPU slot 数（`kind=headless` 默认走 CPU）。见 §12（env：`DSH_BLENDER_QUEUE_CPU`） |
| `features.queue.pending` | number | `64` | 队列里**非终态**作业上限（queued + running）；超了立刻 `queue_full`，不排队等待。见 §12（env：`DSH_BLENDER_QUEUE_PENDING`） |
| `features.queue.ownerQuota` | number | `8` | 单个调用方（hostId+session+agent）最多同时占几个 slot；超了只挡它自己，别的调用方照常准入。见 §12（env：`DSH_BLENDER_QUEUE_OWNER_QUOTA`） |

## 4. blender.exe 怎么被找到

探测顺序（`runtime/blender-detect.ts:detectBlenderExe`；运行期解析在 `runtime/blender-exe.ts`，见 §4.1）：

1. `DSH_BLENDER_EXE` 环境变量；
2. 配置文件 `blenderExe`；
3. **自动扫描**：
   - Windows 官方安装：`%ProgramFiles%\\Blender Foundation\\Blender*\\blender.exe`（按目录列表顺序遍历 `Blender*`，不排序；都没有时回退到 `Blender\\blender.exe` 固定候选），来源记为 `auto:install`；
   - Windows Steam：先读注册表 `HKCU\\Software\\Valve\\Steam`（32 位安装再试 `HKLM\\SOFTWARE\\WOW6432Node\\Valve\\Steam`）的 `SteamPath`（覆盖 G:/H: 与非默认目录；读不到就跳过），再补 `%ProgramFiles%\\Steam`、`%ProgramFiles(x86)%\\Steam`、`%ProgramW6432%\\Steam`，以及 `{C,D,E,F,G,H}:\\{Program Files\\Steam, Program Files (x86)\\Steam, Steam, SteamLibrary}`（按此顺序取第一个存在的根），再读每个根的 `steamapps\\libraryfolders.vdf` 里列出的其它库，命中 `<库>\\steamapps\\common\\Blender\\blender.exe`，来源记为 `auto:steam`（vdf 缺失/损坏时只试根自身，不报错）；
   - WSL：`/mnt/{c,d,e,f}/Program Files/Blender Foundation/Blender*/blender.exe`，以及 `SteamLibrary/steamapps/common/Blender/blender.exe`、`Steam/steamapps/common/Blender/blender.exe`；
   - **macOS**：`/Applications/Blender*.app/Contents/MacOS/Blender` 与 `~/Applications/Blender*.app/Contents/MacOS/Blender`（任意版本名，如 `Blender.app`、`Blender 4.2.app`），以及挂载卷 `/Volumes/*/Applications/…`；
4. `PATH`（Windows `where blender`；Linux `which blender`）；
5. 都没有 → `config.blenderExe = null`（`blenderFrom: not-found`）：`blender_run(action="submit", kind="headless"|"render")` 立即返回 `blender_exe_missing`（含配置指引，不再抛 `TypeError`），提示三种配置方式。

**三种配置方式（任选）**：

```bash
# ① 环境变量
export DSH_BLENDER_EXE=/mnt/d/SteamLibrary/steamapps/common/Blender/blender.exe     # WSL
#   Windows: set DSH_BLENDER_EXE=D:\Program Files\Blender Foundation\Blender 5.2\blender.exe

# ② 包根配置
echo '{"blenderExe":"/mnt/d/.../blender.exe"}' > dsh-blender.config.json

# ③ 用户级配置（多个工程共用）
mkdir -p ~/.dsh && echo '{"blenderExe":"/mnt/d/.../blender.exe"}' > ~/.dsh/dsh-blender.config.json
```

## 5. 工作目录（为什么要"成对"）

Blender（Windows 进程）负责**写**帧 PNG 与无头脚本；宿主（WSL 里的 Node）负责**读**它们。所以需要同一个物理目录的两个写法：

| | 例子 |
|---|---|
| Blender 侧（Windows 路径） | `C:\Users\\<你>\\AppData\\Local\\dsh-blender-rt` |
| 宿主侧（WSL 路径） | `/mnt/c/Users/<你>/AppData/Local/dsh-blender-rt` |

- 默认自动取 Windows 的 `%LOCALAPPDATA%\\dsh-blender-rt`（在 WSL 里通过 `cmd.exe /c echo %LOCALAPPDATA%` 问一次，结果会缓存）；
- 取不到（没有 WSL 互操作 / **原生 Linux**，后者 v1.0.4 起支持）→ 退回 `os.tmpdir()/dsh-blender-rt`（此时要求 Blender 与宿主同机；原生 Linux 上**不做跨 OS 映射**，宿主路径原样交给 Blender，`workDirWin` 与 `workDirWsl` 同构）；
- **WSL 场景不要**配成 WSL 内部路径（如 `/home/me/x`）：Windows Blender 只能通过 UNC 访问，而 **UNC 写入会静默失败**；原生 Linux 上 `/home/me/x` 反而是正确写法；
- 别配到只读挂载（WSL 里 `/mnt/c` 通常只读，除非你在 Windows 侧开了对应权限）。

## 5.5 GPU 语义（无头渲染最贵的坑）

**问题**：无头进程（`blender -b`）**默认读不到用户偏好** → `prefs.compute_device_type = NONE`、设备列表为空 → 即使工程文件里写着 `scene.cycles.device = "GPU"`，**Cycles 也会静默跑 CPU**。
本机实测（1821 对象工程，480×270/32spp）：**CPU 2.78 s vs GPU 预热 0.18 s = 15.4×**。

**三层解法**（按推荐顺序）：

1. **默认的 `gpu:"auto"` 前导**（零配置）：按 `OPTIX→CUDA→HIP→ONEAPI→METAL` 顺序设置 `compute_device_type` + 勾选 GPU 设备 + `scene.cycles.device="GPU"`，并回传 `gpu` 字段（`before/after/configured/fell_back_to_cpu`）；
2. **`use_user_config: true`**：透传 `BLENDER_USER_CONFIG` / `BLENDER_USER_SCRIPTS`（配合 `factory_startup=false`，让无头进程继承你那套偏好与 addon）；
3. **`gpu: "true"`**：要求必须有 GPU，没有就 `ok=false`（不想再被静默降级坑一次时用）。

> 一句话：**别信文件里的 `device=GPU`，要看回执里的 `gpu.after.gpu_enabled`。**

## 5.6 后台作业、GUI 会话与长任务

| 场景 | 用什么 | 说明 |
|---|---|---|
| 一次性重活（渲染/批量几何/校验） | `blender_run(action="submit", kind="headless")` | 冷启动 0.9–1.2 s，干净、可复现；`engine="none"` 跳过前导（纯 numpy/图像任务） |
| **反复迭代 / 看画面** | `blender_py` + `blender_see` | 同一个 GUI 会话内 `K` 持久；`see=true` 同步回帧，约 50–100 ms |
| **渲染 / 相机动画** | `blender_run(action="submit", kind="render")` | 声明式参数（file/frames/resolution/samples/engine/camera），不执行脚本 |
| 单次 > 5 分钟 | 作业层 | submit 立即回 jobId；`wait`/`collect` 收日志与产物，客户端超时 ≠ 任务失败 |

**作业语义**：

- `submit` 没有同步模式；旧无头工具的 `as_job` / `wait_s` 已删除，统一用 `action="wait"` / `"collect"`。旧工具名迁移见 [MIGRATIONS.md](../MIGRATIONS.md) §0.3。
- `blender_run(action="tune", op="status"|"analyze"|"apply"|"revert")` 保留旧 Cycles 渲染分析。
- plan op 需要 ready 的 GUI 会话；catalog、dry-run、help 在本地只读执行，不需要会话。内部 session 池仅服务 `blender_op(action="loop", target="session")` 等内部路由，不是对用户开放的会话工具。

**超时/断连的语义**：客户端断开**不等于任务失败** —— 服务端子进程会继续跑完，产物仍在 `outdir`，全量日志路径在 `logs` 字段里。遇到 `fetch failed` 先翻目录。

## 5.7 virtual-gui 能力门（3.1）

3.1 的 virtual-gui 由 Gateway 拉起一个独立的 Blender GUI 并附着到 provider 提供的显示；它**不是**远程桌面，也不用于最终相机渲染。
能力门默认关闭：Windows 在 V0 验收通过并随发布打开之前为 `off`，通过后默认 `auto`；Linux/macOS 默认 `off`，Linux 只接受显式 `on`（preview，llvmpipe 仅作链路预览）。

Windows 的 W1 provider 已随 3.1 构建提供：Gateway 通过 `vendor/win-hidden-desktop/dsh-blender-hidden-desktop.exe`（开发构建在 `tools/win-hidden-desktop/out/`，可用 `DSH_HIDDEN_DESKTOP_HELPER` 覆盖）启动 Blender，Blender 运行在 helper 创建的私有 desktop 上（不在默认 desktop，任务栏与 Alt-Tab 看不到），窗口保持正常显示而非最小化。helper 缺失、Blender 缺失、helper 提前退出或 ready 超时都会返回结构化错误（`helper_missing` / `blender_exe_missing` / `helper_exited` / `provider_timeout`），不回落默认 desktop；`blender_session stop` 通过 helper 的 job object 连带清理 Blender，重复 stop 幂等。

| 配置 | 行为 |
|---|---|
| `features.virtualGui=off` 或 env `DSH_BLENDER_VIRTUAL_GUI=off` | 不检测、不启动 provider；`blender_session start` 在 spawn 前返回 `stage=config` / `feature_disabled` |
| `auto` | 只在 Windows 生效；非 Windows 归 `off` 并标记 `auto-is-windows-only` |
| `on` | 显式开启；仍要求 provider 实现与全部 prerequisites 就绪，否则同样 fail closed |
| 非法值 | 回退 `off` 并标记 `invalid` |

`blender_session start`、`doctor` 与 `/status` 共用同一份 capabilities：

- `enabled` / `preview` / `ready` / `needs_approval`；
- `prerequisites[]`：每项的 `check`、`install`、`needsRoot` 与当前 `ok` / `detail`；
- `missing[]`、`reason`、`fix`：未就绪时给出可执行修法。

未就绪时启动只返回 `stage=config`（`feature_disabled` / `prerequisites_missing` / `provider_unavailable`），不 spawn Blender/Xvfb，也不静默回落 headless。Linux 的前提是 Xvfb、VirtualGL、Gateway 用户可读的 `/dev/dri/renderD*` 与 Blender；Ubuntu 22.04/24.04 与 Debian 12 的发行版仓库都没有 `virtualgl` 包（2026-11 在 packages.ubuntu.com / packages.debian.org 核对）；必须先添加 VirtualGL 官方 APT 仓库（`github.com/VirtualGL/repo`）再 `apt install virtualgl`，直接安装不是可执行步骤。WSL 不是 3.1 的目标平台。

能力就绪后，`start` 仍需**人类**显式同意。3.3.1 起这件事在会话视图里完成（不再需要离开对话去终端）：

1. **面板（会话视图右侧栏 tab，3.4 迁移）**：「Blender 会话」是右侧栏的一个 tab 类型（`sidebar.right.pane.tab` + 独立注册的 `sidebar.right.pane.tab.title`），由会话头部的入口按钮打开（`conversation.session.header.actions`，有 pending 时带徽标数）；右侧栏服务不可用时自动落到 `shell.overlay` 抽屉。**输入框上方只留一行极简状态**（`Blender · N 待批准`，无 pending 时灰显），点它打开面板 —— 卡片、认领表、策略都不再贴在输入框上。
   面板内容：待批准卡片（请求方 agent/session/role、动作、资源影响「当前实例数 / 上限 / 低内存降到 2」、有效期倒计时、批准/拒绝）、认领表（主 GUI 与每个 virtual-gui 各自一行：instance id、owner 会话、`is_mine`、`viewer`、`borrowed`、heartbeat 年龄、归属剩余有效期、当前 grant）、以及**策略区**（manual / auto / deny 三态 + 当前值 + 来源 + 「改完立即生效，无需重启」）。折叠行同时显示 `待批准 N ｜ 认领 M`。卡片按钮携带的是请求的 `handle`（不是 `request_id`），服务端再映射回请求；决定不 spawn 任何进程，只释放 agent 自己刚发的 `start`。

   3.5 起同一面板下半部分是**只读运维区**（不新增任何会话写路径）：

   - **连接 / 通道**（常显）：后端地址与来源（默认 / 宿主注入 / 插件配置 / 本地面板覆盖）、Gateway `pid` / uptime / RSS、插件版本与 `provenance` verdict、「通道最近 ok 多久前 + 在飞 + 最后命令」、AI 暂停、写租约（holder / 剩余 / scope / holder 是否已退出）、渲染状态与场景名。数据源 `GET /host/state` + `GET /health`（零 Blender 往返）。
   - **作业**：`运行中 N ｜ 共 M` + 最近 6 条（`GET /host/jobs`），每行「日志」读 `GET /host/jobs/log?id=…&tail=6000`。
   - **诊断**（按需，不轮询）：点按钮才取 `GET /status` + `GET /doctor`，显示 verdict、插件版本、addon 就绪实例、Blender 版本/exe、缺口与修法、`next_actions`、`config` 摘要（HTTP / Gateway / workDir / blenderExe / configFile / leaseTtlMs / 平台）。
   - **设置（本机）**：后端地址覆盖（`dsh-blender-plugin:backend`，校验 `http(s)://`、去尾斜杠、空=清除）、轮询间隔（`…:panel:ops-poll-ms`，800–15000 ms；有作业/渲染时自动 1000 ms）、原始快照开关。**只写浏览器 localStorage**，不改 owner / grant / `virtualGuiConsent`。
   - 认领表每行补 kind / status 与「复制 attach」（`blender_session action=attach instance_id=…`）。

2. **批准即续跑**：manual 策略下 `start` 落一条待批准请求（`<workDir>/consent/<request_id>.json`，15 分钟有效、同一调用方复用）后**等待**人类决定（默认 20 s，工具参数 `wait_ms` 可调，上限 120 s）。人在面板点「批准」→ 同一次调用立即继续，回执 `consent_source=approved_request`（点完之后 ≤2 s 落地）。等满仍未决定则回 `state=pending` + `request_id`：再调一次 `start` 即消费这次批准，人不需要再做什么。**批准只消费一次**，用掉的请求标记为 `consumed`。

3. **策略 auto / manual / deny**（落 profile、热生效）：

   | 写法 | 行为 |
   |---|---|
   | `manual`（默认，旧名 `ask`） | 落请求 + 面板卡片 + 等待；回执 `state=pending` / `consent_source=approved_request` |
   | `auto`（旧名 `allow`） | 不弹卡片，直接放行，回执 `consent_source=policy:allow`；**面板常显「自动批准已开」** |
   | `deny` | 一律拒绝，`reason=policy_denied`，不 spawn |

   三种写法任选其一（优先级从高到低）：
   - 环境变量 `DSH_BLENDER_VIRTUAL_GUI_CONSENT=auto|manual|deny`；
   - profile 的插件配置键 `virtualGuiConsent`（宿主在拉起 Gateway 时注入成上面那个环境变量，HMR 换代即生效）；
   - 配置文件 `dsh-blender.config.json` 里的 `{"virtualGuiConsent":"auto"}` 或 `DSH_BLENDER_CONSENT_POLICY_FILE` 指向的文件 —— **每次调用重读**，改完 ≤250 ms 生效，不重启 DSH、不重启 Blender。

   面板顶部永远显示当前 `mode` 与来源（`default` / `env:…` / `file:…`），auto 时另有一行常显提示 —— 不会只在配置文件里体现；切到 auto 需要**二次确认**（第一下变「确认自动批准」，第二下才提交）。

6. **请求文件的保留与节流**：请求落盘在 `<workDir>/consent/`，超过 7 天或超出最近 200 个的文件会被清理（仍 pending/approved 的不删，10 分钟扫一次）；同一调用方 **60 s 内最多落一条新请求**（`DSH_BLENDER_CONSENT_MIN_INTERVAL_MS`，默认 60000，0=关闭），被挡时 `start` 回 `reason=rate_limited` + `retry_after_ms`，`consent_request` 回 `consent_rate_limited`。

   终端仍然可用（等价通道）：`curl.exe -s "http://127.0.0.1:39877/lease?action=consent_approve&requestId=<request_id>"`（`consent_deny` 同理；query-string 形式，PowerShell/bash 都不用 JSON 引号，不需要 DSH 身份头）。

4. **策略切换（唯一新增写路径）**：面板里点 auto / manual / deny 直接改配置，落到
   `POST /lease {"action":"consent_policy_set","mode":"manual|auto|deny"}`。

   - 门：只接受回环 Origin（或没有 Origin 的终端）+ **无 DSH 身份头**；带 `X-DSH-*` 一律 **403 `consent_human_only`**（agent 不能改策略，这条比 approve 更要紧）。
   - 只写插件配置键 `virtualGuiConsent`（`DSH_BLENDER_CONSENT_POLICY_FILE` → `DSH_BLENDER_CONFIG` → 已有配置文件 → `~/.dsh/dsh-blender.config.json`），**其它键一个不动**；写前在文件旁留 `.bak`，原子写（tmp + rename）。
   - 回执：`{ok, policy:{mode,policy,auto,source,file}, effective:'immediate', audit:{at,origin}, backup?, previous?, created?}`。
   - **env 锁定**：若 Gateway 进程有 `DSH_BLENDER_VIRTUAL_GUI_CONSENT`，面板显示「被环境变量 … 锁定」并禁用全部三态控件，`consent_policy_set` 回 **409 `policy_locked`**（不会出现"改了但被覆盖"的假象）。
   - 浏览器 POST 需要预检：`OPTIONS /lease` 只对回环来源回 204 + CORS 头。

5. **数据面（只读）**：`GET /lease?action=consent_panel&dshSessionId=<会话 id>` 返回 `policy`（mode/policy/auto/source/file）、`resources`（instances / limit / low_resource / ready_instances）、`requests[]`（handle/state/expires_in_ms/caller）、`sessions[]`（与 `blender_session status` 同源：id / instanceId / owner（含 `heartbeat_age_ms`、`expiresInMs`）/ `is_mine` / `borrowed` / viewer / grants）。只接受**回环来源**（`127.0.0.1` / `localhost` / `dsh-app://`）或没有 `Origin` 的终端请求，其它来源 403 `origin_not_allowed`。

**模型侧没有任何“自己批准自己”的路径**（3.3.2 收口）：

- 工具面只保留 `consent_request` / `consent_status`（看请求与策略）；`consent_approve` / `consent_deny` 已从 `blender_session` 的动作表移除，误调回 `consent_human_only`；
- HTTP 面：**任何带 DSH 身份头**的 `consent_approve` / `consent_deny` 一律 403 `consent_human_only`（agent 直接 curl 也过不去），只有无身份头的人类通道（会话面板 / 终端命令）能决定；
- 无人值守走策略 `virtualGuiConsent=auto`（人写的配置文件 / 环境变量），不经过任何工具调用。

token 仍是一次性 30 秒且绑定调用方；重放/过期继续要求重新决策，不会自动退回 headless 或 user-gui。`consent_status` 额外回 `mode` / `auto` / `policy_source`。

启动成功后的会话 id 为 `virtual-gui:<instanceId>`，只有 Gateway 拉起的那个 Blender 以同一 `instanceId` 完成 addon 握手才标记 `ready`（provider 通过 `DSHBB_INSTANCE_ID` / `DSHBB_SESSION_KIND=virtual-gui` 注入），握手超时为 30 秒；任何失败（provider 启动失败、握手超时）都会先停掉 provider，不留 Blender 进程或半注册会话。`stop` 只接受会话所有者，成功后会话与进程一起消失，重复 `stop` 返回 `stopped:false`。

同时存活的 virtual-gui 默认上限为 4（`features.virtualGuiMax` / env `DSH_BLENDER_VIRTUAL_GUI_MAX`，允许 1–16）；总内存不足 16 GiB 或空闲内存不足 4 GiB 时自动降到 2。超限时 `start` 在 spawn 前返回 `stage=session` / `capacity`，evidence 带 `used` / `limit` / `configured` / `low_resource` / `reason`；已有会话可以 stop 或复用，不会排队等待。

### 5.7.1 发行版前提与一键安装

`/doctor` 的 `virtualGui.installPlans` 是唯一安装计划来源：TUI 的 `doctor --fix` 与 addon 偏好设置按钮共用同一份计划。插件与扩展安装过程本身绝不运行包管理器。

| 平台 / 发行版 | 前提 | 一键安装 | 手动命令 |
|---|---|---|---|
| Windows 11 | hidden-desktop helper + Blender 4.2.10 | 无 | helper 随 3.1 包提供；缺 Blender 时设 `DSH_BLENDER_EXE` |
| Ubuntu 22.04 / 24.04、Debian 12 | `xvfb` | **是**：`pkexec apt-get install -y xvfb`（需要 polkit） | 无 pkexec 时：`sudo apt-get install -y xvfb` |
| Ubuntu 22.04 / 24.04、Debian 12 | `virtualgl`（硬件 GL；缺失只降为 preview-only） | 否 | 先加官方 APT 仓库（`github.com/VirtualGL/repo`）→ `sudo apt-get update` → `sudo apt-get install -y virtualgl`；发行版仓库没有该包，不能直接 `apt install virtualgl` |
| Ubuntu / Debian | Gateway 用户可读 `/dev/dri/renderD*` | 否 | `sudo usermod -aG video,render $USER`，然后注销重登；驱动只检测不安装 |
| Fedora | `xvfb` / `virtualgl` / `/dev/dri` | 否 | `sudo dnf install -y xorg-x11-server-Xvfb`；VirtualGL 走官方仓库，注意 `$USER` 与注销重登 |
| Arch | `xvfb` / `virtualgl` / `/dev/dri` | 否 | `sudo pacman -S --needed xorg-server-xvfb`；VirtualGL 走官方仓库 |
| macOS | provider | 无 | 3.1 不支持 virtual-gui；用 user-gui 或 blender_run(kind=render) |

一键入口有两个，都读同一份 `/doctor` 计划：

- DSH TUI：`/blender doctor --fix` 显示缺失前提与命令；支持一键的项执行显示过的 argv（`pkexec`），完成后自动复检 capabilities。
- Blender add-on Preferences：「Virtual Display (virtual-gui)」→ **Install missing prerequisites**。只执行支持的一键命令，其余显示手动命令和原因；安装失败保留原始 stderr，且不会把 provider 标为 ready。

不装依赖就不可用：启动路径在 spawn 前检查 prerequisites，任何缺失都返回 `stage=config`（`prerequisites_missing` / `feature_disabled` / `provider_unavailable`），不启动 Xvfb/Blender，不回落 headless，也没有 force/unsafe 绕过开关。

### 5.7.2 平台限制与 preview 语义

- Windows：非管理员控制台会话已实测（5.5，32/32）；RDP 无会话环境暂不可测，锁屏会锁住用户桌面，因此不作为自动验收场景；这两项按限制记录，不算通过项。
- Linux：virtual-gui 是 **opt-in preview**，默认关闭。`vglrun`/`/dev/dri` 不满足时 provider 以 llvmpipe 启动并标 `preview-only`，不得当成硬件 GL 证据；不提供 user-gui parity 承诺；最终相机渲染一律用 `blender_run(kind="render")`，不拿 virtual-gui 当渲染机。
- WSL 不是 3.1 目标平台；WSL 的 Xvfb/D3D12 结果只作技术参考，不能替代 Linux preview 验收。

## 11. 无头作业、等待窗口与产物路径

### 11.1 等待窗口与作业语义

等待窗口不是环境变量，而是**每次调用传** `timeout_ms`（夹在 1–600 s，客户端静态预算再加 30 s 余量）：

| 入口 | 行为 |
|---|---|
| `blender_run(action="submit", …)` | 立即回 `jobId`（队列提交体 `surface=queue`、`op=submit`），不等结果 |
| `blender_run(action="wait", id=…, timeout_ms=…)` | 阻塞到完成或该预算用尽；超时回 `timed_out: true`，作业**继续跑** |
| `blender_run(action="collect" / "status" / "list" / "cancel", id=…)` | 随时看进展、收日志与产物、或中止 |

> 语义：`wait` 超时**不是失败** —— 服务端进程照跑、产物照落盘，用 `blender_run(action="collect", id=…)` 按 id 回收即可。结果取回前回执的 `verdict` 只到 `degraded`（作业已建立、证据还没到）。
> 排队相关的容量键（`features.queue.*`）与「为什么这个作业还没开始」的解释见 §12。

**验收（复制即跑）**：

```python
# ① submit 立即回 jobId；wait 按 timeout_ms 等，到点回 timed_out 而不是 deadline 报错
r = blender_run(action="submit", kind="headless",
                script="import time; time.sleep(200); print('HEADLESS {}')", timeout_ms=900000)
blender_run(action="wait", id=r.jobId, timeout_ms=100000)
blender_run(action="collect", id=r.jobId)      # 收日志与产物

# ② 不等待：submit 后直接拿 jobId 走人
blender_run(action="submit", kind="headless", script="print('HEADLESS {}')")
```

> 与 §5.6「客户端超时 ≠ 任务失败」的关系：这条现在**有句柄可收** —— 回执里直接给 `jobId`，不用再靠 `ls` 看 PNG 时间戳猜。

### 11.2 `outdir` / `out_json` 接受 WSL 路径

| 参数 | 当前行为 |
|---|---|
| `blender_run(kind="headless", outdir=…)` | **接受 WSL 路径**（`/home/…`、`/mnt/…`），内部用 `K.win_path` 映射；回执给真实写入路径（Windows + WSL 两种形态） |
| `blender_run(kind="headless", out_json=…)` | 同上；大结果自动溢出也落真实产物目录 |
| 脚本把 `/home/…` 交给 Windows 侧 API | 检测到就**显式报错**，不再静默漂移 |

```python
blender_run(action="submit", kind="headless",
  outdir="/home/sixtyseven67/DSH/.tmp/hull_aft",     # ✅ 直接给 WSL 路径
  script="import os, json; open(os.path.join(K.out_dir, 'probe.txt'), 'w').write('ok'); "
         "print('HEADLESS ' + json.dumps({'out': K.out_dir}))")
```

```bash
# 跑完在 WSL 侧核对（回执里也会给 Windows 形态 + WSL 可见形态两份真实路径）
ls -la /home/sixtyseven67/DSH/.tmp/hull_aft/probe.txt
```

**红线（不变）**：

- `/mnt/c|d|e|f` 是**只读挂载** —— 写不进去；
- 产物落在只读挂载 → `read_image` 打不开，每轮要多一次 `cp` 才能看图；
- **不要**往 UNC（`\\wsl.localhost\…`）写：可能"返回成功但没有文件"；
- 临时文件落**工作区**（bash 沙箱的 `/tmp` 与 fs 工具不共享，见 [操作教程.md](操作教程.md) §7.5）。

### 11.3 与 §5「工作目录必须成对」的关系

两件事，不冲突：

| | 谁的要求 | 怎么写 |
|---|---|---|
| **§5 插件 `workDir`** | 插件自身（帧 PNG / 无头脚本的落点；Blender 侧要能直接写） | 仍建议配 **Windows 形态**（`D:\…`），插件自动映射出 WSL 形态 |
| **§11.2 调用级 `outdir` / `out_json`** | 每次调用的产物目录 | **可以直接给 WSL 路径**，映射由插件做 |

## 12 作业队列容量（`features.queue` / `DSH_BLENDER_QUEUE_*`）

队列容量**不是编译期常量**：`runtime/config.ts` 按「env → 配置文件 → 默认值」解析，
`runtime/gateway/app.ts` 把四个值整套交给 `JobQueue`，并把**存活的 virtual-gui 数量**作为 GPU 预留一起算。
没有自适应：默认恒为 **1 / 2 / 64 / 8**，同一台机器不会今天 2 个槽、明天 1 个。

| 键 | env | 默认 | 语义 | 低资源行为 |
|---|---|---|---|---|
| `features.queue.gpu` | `DSH_BLENDER_QUEUE_GPU` | `1` | 同时跑的 **GPU slot** 数：`kind=render`，以及 `gpu=true` 的 headless | 默认已是 1，小显存机器**不用改**；要并行先确认显存够两个进程（两个 render 各占一份，见 §12.1） |
| `features.queue.cpu` | `DSH_BLENDER_QUEUE_CPU` | `2` | 同时跑的 **CPU slot** 数：`kind=headless`（未显式 `gpu=true`） | 少核 / 小内存机器设 1 即可；`0` 与负数非法，回落默认 |
| `features.queue.pending` | `DSH_BLENDER_QUEUE_PENDING` | `64` | 队列内**非终态**作业上限（queued + assigned + running）；达到上限后 `submit` **立刻**返回 `queue_full`，不进入无限等待 | 磁盘/内存紧张时设 8–16；这是 `queue_full` 文案唯一点名的键 |
| `features.queue.ownerQuota` | `DSH_BLENDER_QUEUE_OWNER_QUOTA` | `8` | 单个调用方（hostId + dshSessionId + agentId）同时占用的 slot 上限；超限的作业留在 `queued`，其它调用方的作业照常准入（不饿死） | 多个子代理共用一台机时设 2–4，避免一个会话吃满所有槽 |

**写法（任选其一）**：

```bash
# ① 环境变量（优先级最高）
export DSH_BLENDER_QUEUE_GPU=2 DSH_BLENDER_QUEUE_PENDING=16

# ② 配置文件（$DSH_BLENDER_CONFIG / <包根>/dsh-blender.config.json / ~/.dsh/dsh-blender.config.json）
# {"features": {"queue": {"gpu": 2, "cpu": 4, "pending": 16, "ownerQuota": 4}}}
```

非法值（非数字 / `0` / 负数）**回落默认**，来源记成 `invalid:env:…` 或 `invalid:file:…`（`CFG.features.queueSource`），
不会被当成"默认值"糊过去——配了没生效能看出来。

### 12.1 `gpu=1` 时第二个 render 会排队

默认只有 1 个 GPU slot。第一个 `kind=render` 占满它期间，第二个 render 停在 `queued`：
`status` / `list` 的结构化行里 `decision.outcome=waiting`、`reason=capacity`（`status` 另带
`detail=target slot is busy`），事件链是 `queued/submitted`（**不是**失败）。
想真并行渲染，把 `features.queue.gpu` 设成 2——但先确认显存够两个进程（Cycles/OptiX 会各自占一份）。

### 12.2 virtual-gui 占 GPU slot

每个 `starting`/`ready` 的 virtual-gui 会话预留 1 个 GPU slot（`reservedGpu = sessionRegistry.virtualGuiCount()`）。
默认 `gpu=1` + 1 个 virtual-gui ⇒ **所有 render 停在 `queued`**，原因写 `virtual_gui`
（`detail=target slot is busy`）。要边看边渲就把 `gpu` 调到 2；virtual-gui 只适合预览，
最终相机渲染仍走 `blender_run(kind="render")`（§5.7）。

### 12.3 `wait` 超时 ≠ 失败

`wait` 是"我最多等这么久"：到点回 `waitTimedOut: true`（工具层 `timed_out`）且**不取消作业**。
工具层同时给 `still_running: true`（队列层不带该字段时按 false 落，不编造"还在跑"）；配合 `state` 区分：`running` = 在跑、`queued` = 还没拿到槽位（看 `decision.reason`）。
作业继续跑、产物照落盘，用 `action="status"` / `action="collect"` 按 id 回收（§11.1）。
排在别人后面的作业更容易撞上超时——它是**还没开始**，不是**跑失败了**：
`status` 的 `state=queued` + `decision.reason` 会说明它为什么还没开始。

### 12.4 怎么查当前生效的值

```bash
curl -sS -X POST http://127.0.0.1:39877/job -H 'content-type: application/json' \
  -d '{"surface":"queue","op":"perf"}' | python3 -m json.tool
```

或让模型调 `blender_run(action="perf")`：

- `capacity`：四个容量（`gpu` / `cpu` / `pending` / `ownerQuota`）；
- `slots.gpu.reserved`：当前被 virtual-gui 预留的 GPU slot 数；
- `pending`：当前非终态作业数（和 `capacity.pending` 比就知道离 `queue_full` 还有多远）。

### 12.5 `queue_full` 怎么解

`queue_full` 的 `fix` 直接点名 `DSH_BLENDER_QUEUE_PENDING`（或配置文件 `features.queue.pending`），
`evidence` 带 `{pending, limit, set}`。先 `blender_run(action="list")` 看是不是有一堆已结束但没 `collect`/`cancel` 的作业，
再决定"等它跑完"还是"调大 pending"。调大只影响准入，不增加真实算力。
