## D-1 doctor 与 virtual-gui 的实际可用性不一致

**现象**：`doctor` 显示 `virtual-gui enabled · ready`，但同 caller `start kind=virtual-gui` 起不来。

**为什么**：可用性其实由**"本 caller 是否已有 ready user-gui"**决定，而 doctor 只报了能力开关。
定位：`runtime/http/routes/health.ts:211`（`ready_instances` 已统计）、`runtime/core/sessions/display-gate.ts:57-74`（viewer / 占用判定）、`runtime/core/sessions/attach.ts:74-80`。

**修法**：doctor 的 virtual-gui 段增加一项 `available_for_caller`，判据与 `display-gate` 同源；不可用时 `reason` 写"another caller holds the ready user-gui"或"same caller already owns one"。
**验收**：① 空载 → `available_for_caller=true`；② 主控占用后 → `false` 且 `reason` 命中；③ `doctor` 与 `start` 的结论不再矛盾。

## D-2 拒绝时的引导不足

**现象**：回执 `session_already_available — a ready user-gui session already exists for this caller`（本项目 6/6 复现）。信息对，但没给出路。

**修法**：错误体带三条 `fix`：`detach` 后重试 / 换一个 caller（另一 `agentId`）/ 直接用现有会话（`attach` + `grant`）。与现有 `code/stage/fix/fallback` 结构保持一致。
**验收**：回执里 `fix[]` 至少两条可机械执行。

## D-3 render 拒收 script（能力缺口）

**现象**：`kind=render` 带 `script_file` 直接拒（`queue_render_script`），多机位一进程渲染只能退回 `kind=headless`，于是丢掉 render 的声明式参数（相机/帧/通道）。

**定位**：`runtime/core/queue/manager.ts:135-142`。
**修法**（择一，推荐 a）：
a) render 增加 `pre_script`（只允许在渲染前跑一次，禁止改输出参数）；
b) render 支持 `cameras: string[]`，一次提交按机位轮转；
c) 不改代码，文档写明"多机位 = headless + 自己循环"，并把 render 的声明式参数在 headless 侧补齐。
**验收**：a/b 任一条能让"一次提交 → 多机位产物"成立，且 `channels` 收尾仍生效。

## D-4 collect 的 tail 按字符切

**现象**：`tail` 默认值下结构行被切半（本项目 `STK_JSON` 被截断，必须 `tail=60000` 重取）。
**修法**：`tail` 改为**按行**保留最后 N 行（新增 `tail_lines`，`tail` 保留兼容并文档标注"字符"），或截断点回退到最近换行。
**验收**：给一条超长日志，`tail=2000` 时输出以完整行结尾。

## D-5 临时脚本路径与 traceback 错位

**现象**：headless 把脚本拷到 `%LOCALAPPDATA%\dsh-blender-rt\tmp\dsh-job-*` 再执行，traceback 里的文件/行号指向临时副本。
**定位**：`runtime/core/queue/spawn-executor.ts:32`（`mkdtempSync(dsh-job-)`）、`runtime/config.ts:317-341`（tempRoot 三级回落）。
**修法**：失败回执带 `script_map: {temp_path → source_path}`，并在 text 里用一行写明"traceback 行号对应临时副本，删除后不再可读"；可选保留临时目录到 collect 之后。
**验收**：故意制造语法错误，回执能给出源脚本路径。

## D-6 `//` 的解析基准

**现象**：`output="//…"` 落到了 .blend 所在目录（`blends/renders/`），不是 `outdir`。
**修法**：文档在 `blender_run` 一节写明"Blender 相对路径语义：`//` = .blend 所在目录，与 `outdir` 无关"；或在 `outdir` 与 `//` 同时出现时回执 warning。
**验收**：文档改完 + 一条 warning。

## D-7 viewer 的真实能力边界

**现象**：子代理 `attach` 得到 `viewer=true · is_mine=false · borrowed=true`，`blender_py` 写入被拒（合理），但**只读的 `blender_inspect` 也可能在 addon 层被拒**（历史实测；本项目未触发）。→ "viewer = 只读可见"这个说法不成立。

**定位**：`runtime/core/sessions/attach.ts:74-80`、`display-gate.ts:65-68`。
**修法**：二选一并写进文档：a) viewer 明确放行所有只读命令（addon 侧 gate 加白名单）；b) 改名"viewer = 只能看画面，不含数据查询"，并把 `blender_inspect` 在 viewer 下的失败回执写成 `viewer_cannot_inspect` 而不是笼统拒绝。
**验收**：viewer 身份下 `blender_inspect command=help` 的结论与文档一致（能跑或明确不能跑）。

## D-8 worker 的 see 与 blender_see 对齐

**现象**：worker 的 `see` spec 没有 `fit=object` / 正交档位，自证取景要自己建相机算 NDC。
**定位**：`runtime/execution/workers/index.ts:153`（`workerCall(op:'see', spec)`）。
**修法**：把 `blender_see` 的 `custom/fit/ortho` 字段下沉到 worker spec 白名单，缺字段时回执说明"该档位仅 GUI 侧支持"。
**验收**：worker 内 `see spec={fit:"object", ortho:true}` 出图与 GUI 同参数一致（尺寸容差 ±2 px）。

## D-9 GPU 车道与容量（与 90 号合并）

**现象**：四线并行时 `QUEUE_FULL` / 排队；`priority` 在渲染上未验证。
**定位**：`runtime/core/queue/types.ts:123`（`gpu:1`）、`runtime/gateway/app.ts:118`（未传 capacity / reservedGpu）。
**修法**：见 90 号 P0-1 / P0-2（容量可配 + 接上 `reservedGpu`），并补一条"priority 在 render 上实测"的用例。
**验收**：两个 render 并发提交时 `status` 能看到 `decision.reason`。

## D-10 `worker closed` ≠ 不可用

**修法**：文档标注 worker 端口懒启动；`status` 里该字段改叫 `worker_idle` 或加一行说明。
**验收**：文档改完即可。

## D-11 owner 所有权可能被抢

**现象**：主控在 owner TTL 内长时间不调用，所有权可能被 attach 的子代理拿走（历史实测，本项目靠每轮 attach 保活未复发）。
**修法**：先复现（写一条集成用例：owner 心跳过期 + 并发 attach），再决定是"续期策略"还是"attach 不得夺取"。
**验收**：用例能稳定复现后，修复使 owner 在 TTL 内一定不被夺。

## D-12 user-gui 在用时，同一台机器上谁都不能开 virtual-gui

**现象**：主控占用 user-gui 后，子代理（甚至同机其他 DSH 会话）`start kind=virtual-gui` 一律被拒，回执 `session_already_available`（本项目 6/6 复现），于是"子代理用虚拟 GUI"在这台机器上不可达。

**判据链**（这是关键，不是猜测）：

```
runtime/core/sessions/virtual-gui.ts:149   existing: this.host.findForCaller(caller)
        → display-gate.ts:55-79            if (existing.kind === 'user-gui' && existing.status === 'ready') → fail
        → lookup.ts:65-76                  findCallerSession 的三条命中：inOwnerFamily / readableBy / agents.has
        → types.ts:196-215                 inOwnerFamily 含"子代理（parent=owner）"；readableBy = sameHost
```

也就是：**主控的子代理、以及同机任何能"读到"这个会话的 caller，都会命中同一个 user-gui**，于是全被挡。

**性质判断**：**意图是设计，判据是失误**。
- 设计意图真实：一个 caller 不该同时拥有两个 GUI；人类正在用的窗口不该被 agent 抢；`virtualGuiMax`（默认 4）+ 内存闸门证明"多开会话"本身是被允许的。
- 失误在于**用"可读"当"占用"**：`readableBy = sameHost`（`types.ts:214-216`，注释写着"reads are cross-visible on the same machine"）本是给只读旁观者用的，却被复用成了资源占用判据 → 独占范围被人为放大到全机。
- 后果：`doctor` 说 `ready`、`start` 说不可用（D-1 同源），并行形态被迫退化成"一线一个 .blend + 全 headless"。

**修法**（三步，互不依赖）：

1. 判据收窄：`existing` 只取"我拥有的"——`ownerMatches(owner, caller) || session.agents.has(callerKey(caller))`，去掉 `inOwnerFamily` 与 `readableBy` 命中。
2. 放开并存：user-gui 与 virtual-gui 允许同时存在，数量只受 `features.virtualGuiMax` + `systemVirtualGuiLimits` 的内存闸门约束（已有实现，直接复用）。
3. 文案三分：`你已拥有` / `别人拥有（只读可见）` / `无人拥有（可 claim）`，每种都给真实出路（释放、claim、或直接 attach + grant）。

**验收**：① 主控占 user-gui 时，子代理 `start virtual-gui` 成功且拿到独立 `instanceId`；② 同一 caller 再开第二个 user-gui 仍被拒（这条不能破）；③ 3 个 virtual-gui + 1 个 user-gui 并存，`session list` 四个都在且 `is_mine` 正确；④ 显存/内存不足时降到 2 的行为仍生效。

## D-13 内存门只看"启动那一刻"，没有单实例成本模型

**现状**（`runtime/display/limits.ts:10-71`）：每次 `start` 前调 `systemVirtualGuiLimits()`，读一次 `os.totalmem()` / `os.freemem()`，按两条硬阈值判：

```
total < 16 GiB  或  free < 4 GiB  →  limit = min(configured, 2)
否则                              →  limit = clamp(configured, 1..16)
configured = env DSH_BLENDER_VIRTUAL_GUI_MAX > features.virtualGuiMax > 4
```

判定点在 `virtual-gui.ts:153-155`：`used = virtualGuiCount()`，`used >= limit` 才拒。

**问题（四条）**

1. **没有单实例成本**：`limit` 是"个数"，不是"预算"。4 个隐藏 Blender 各吃 1–2 GB，在 free=4.1 GiB 时照样能一次放进来 4 个。
2. **快照而非预算**：只判"当前 free 够不够阈值"，不判"放进来之后够不够"；启动后也不再复核（无降级、无拒绝回收）。
3. **与作业队列不共享视野**：同时跑 4 个 headless 渲染（`cpu:2`/`gpu:1`）会吃掉内存，但 virtual-gui 的判定看不到作业占用。
4. **阈值是常数占位**：`limits.ts:5-8` 的注释自己写着"low-resource ceiling is a placeholder that the V0 report will confirm"。

**修法**：把"个数上限"换成"预算式准入"，仍复用现有常数作为上下界：

```
reserve_host   = 2 GiB                       // 留给系统与宿主
per_instance   = 1.5 GiB                     // 实测每实例（helper+Blender）峰值
admit  iff  used < configured  &&  (used + 1) * per_instance + reserve_host <= freemem
```

并做三件小事：① `start` 后 5 s 复测一次，超预算记 `degraded:memory` 而不强杀；② 把 `VirtualGuiLimits` 透到 `doctor` / `status`（`limit / used / free / reason`），与 D-1 一起改；③ 作业队列准入时把 `virtualGuiCount()` 计入 `reservedGpu` 同类的预留（见 D-9）。

**验收**：① 16 GiB 机器上 free=4.5 GiB 时，第 3 个实例被拒且 `reason=memory`；② 关掉 2 个作业后能立刻放行；③ `doctor` 能读出 `limit/used/free` 三个数。
